You can also use `--array 1-50` if you prefer 1-based indexing. - **`--mem=4G`** allocates 4 GB per array task. If you need memory *per CPU* instead, use `--mem-per-cpu=4G`. - **`-o output_%A_%a.out`** uses Slurm's built-in job-array output formatting: - `%A` = the main job ID - `%a` = the array task index - This produces files like `output_12345_0.out`, `output_12345_1.out`, etc., one per task. - **`SLURM_ARRAY_TASK_ID`** is an environment variable set by Slurm that holds the current task's index (0–49). Use it in your command to select per-task inputs or parameters. ## Submit ```bash sbatch my_array_job.sbatch ``` ## Check status ```bash squeue -u $USER -J my_array_job ``` Would you like help tailoring the command inside the script to your specific program or input files?

⚠️ Status: PARTIALLY CORRECT (1/2 sources found)

🤖 archi's Answer
Here's the key difference: **Home directories** (`/n/homeNN/yourlogin`) are for everyday files—scripts, configs, small datasets. They have a 100 GB hard limit, are backed up daily, and have moderate performance. **They are not appropriate for I/O-intensive work or large numbers of jobs** [Home and Lab directories](https://docs.rc.fas.harvard.edu/kb/cluster-storage/). **Scratch** (`/n/netscratch` or local `/scratch`) is high-performance temporary storage. It's not backed up, has a strict 90-day retention policy (files get purged), and is designed for large, I/O-heavy jobs [Scratch – FASRC DOCS](https://docs.rc.fas.harvard.edu/kb/policy-scratch/). **For intermediate job output, use scratch** — specifically: - **`/n/netscratch`** for shared, high-performance scratch across all nodes (your lab gets 50TB) - **`/scratch`** (local to each compute node) if you need the fastest possible I/O and your job runs on a single node Use home only for final results you want to keep, or for small, non-I/O-heavy files.
✅ Expected Answer
Home directories are small (~100 GB), backed up, and intended for code, config, and important small files. `/n/holyscratch01/` is large, fast, and not backed up; it is purged on a published schedule and is the right place for intermediate job output and large working datasets. Move final results out of scratch before the purge window.

My batch job on bigmem is being OOM-killed after it climbs past 250 GB of resident memory. What should I check, and what's the right way to request more memory?

⚠️ Status: PARTIALLY CORRECT (1/3 sources found)

🤖 archi's Answer
Here's what you should check and how to fix it: ## What's happening Slurm imposes a default memory limit of **100 MB per node**. If your job exceeds that, it gets killed with `OUT_OF_MEMORY` status. Since your job is climbing past 250 GB, you clearly need to request much more memory. ## How to request more memory Add this to your batch script: ```bash #SBATCH --mem 300G ``` Replace `300G` with a value slightly above your actual peak usage. You can use `M` for megabytes or `G` for gigabytes. ## How to determine the right value 1. **Run `jobstats`** on a completed (successful) job to see its actual memory peak: ```bash jobstats YOUR_JOB_ID ``` > Note: If the job exited with `OUT_OF_MEMORY`, the recorded memory is inaccurate. You need a successful run to get the true peak. 2. **Set `--mem` slightly higher** than what `jobstats` reports, since `--mem` is a hard upper limit. 3. **Start conservatively** — the scheduler finds nodes more easily when you request smaller amounts. Job slots average about 4000 MB per core, but most jobs need far less. ## Multi-node caveat For multi-node jobs, `--mem` is the maximum memory on **any single node**. If you're not using `--ntasks-per-node` to control task placement, memory usage can vary between runs. ## Quick checklist - [ ] Add `#SBATCH --mem XG` (or `XM`) to your script - [ ] Run a test job to completion and check with `jobstats` - [ ] Increase `--mem` to something above the peak reported - [ ] Resubmit For more details, see [Slurm memory limits](https://docs.rc.fas.harvard.edu/kb/slurm-memory-limits/).
✅ Expected Answer
First confirm the kill with `sacct -j --format=JobID,State,ExitCode,MaxRSS,ReqMem` — `MaxRSS` shows the peak used and `State=OUT_OF_MEMORY` confirms the OOM. To raise the limit, increase `--mem` on the sbatch directive (the bigmem partition supports requests up to its documented per-node ceiling — check the partition page for the exact value). Also check whether your code is leaking, using mmap incorrectly, or could shard the workload across an array.

My MPI Python script using mpi4py hangs after one rank finishes its work and exits. How should I structure my Slurm submission with srun for proper teardown across multiple nodes?

🎯 Retrieval Check

Expected Document(s): https://docs.rc.fas.harvard.edu/kb/mpi-jobs/, https://docs.rc.fas.harvard.edu/kb/running-jobs/, https://docs.rc.fas.harvard.edu/kb/python-on-cluster/

⚠️ Status: PARTIALLY CORRECT (1/3 sources found)

🤖 archi's Answer
Based on the FASRC documentation and Slurm MPI guidance, here's how to structure your Slurm submission to avoid mpi4py hangs: ## The Problem When one MPI rank finishes early and exits while others are still running, the remaining ranks may hang waiting for communication (e.g., a collective operation or implicit barrier). Slurm's default behavior can compound this by not properly cleaning up the job step. ## Recommended Structure ### 1. Use `srun` with `--mpi=pmix` (or `--mpi=pmi2`) FASRC recommends using `srun` with an explicit MPI plugin rather than letting `mpirun` manage tasks externally. This ensures Slurm monitors and tears down all ranks properly: ```bash #!/bin/bash #SBATCH -n 64 # Total MPI ranks #SBATCH -t 60 # Runtime #SBATCH -p sapphire # Partition #SBATCH --mem-per-cpu=2000 # Memory per CPU in MB module load openmpi/5.0.10-fasrc01 # Run your Python script with srun, specifying the MPI plugin srun -n $SLURM_NTASKS --mpi=pmix python my_mpi_script.py ``` See the FASRC [Running Jobs](https://docs.rc.fas.harvard.edu/kb/running-jobs/) guide for the full pattern. ### 2. Ensure All Ranks Reach `MPI_Finalize` In your Python script, make sure **every rank** calls `MPI.Finalize()` (or `mpi4py` equivalent) before exiting, even if a rank has no work to do. A common pattern: ```python from mpi4py import MPI import sys comm = MPI.COMM_WORLD rank = comm.Get_rank() if rank == 0: # Do work... pass # Ensure all ranks reach this point comm.Barrier() # Optional: explicit barrier if needed # All ranks must reach Finalize MPI.Finalize() ``` ### 3. Use `--kill-on-bad-exit` (if available) If your Slurm version supports it, add `--kill-on-bad-exit` to `srun` to ensure remaining ranks are killed if any rank exits abnormally: ```bash srun --kill-on-bad-exit -n $SLURM_NTASKS --mpi=pmix python my_mpi_script.py ``` ### 4. Avoid Implicit Barriers If your code uses collective operations (e.g., `comm.Allreduce`, `comm.Bcast`), ensure **all ranks** participate. If a rank exits early, it will not participate, causing a hang. Use conditional logic or explicit barriers to handle ranks with no work. ## Key Takeaways - Use `srun -n $SLURM_NTASKS --mpi=pmix` rather than `mpirun` to let Slurm manage the job step lifecycle. - Ensure all ranks reach `MPI.Finalize()` — even idle ranks. - Avoid collective calls from ranks that might exit early. - Consider `--kill-on-bad-exit` for robust cleanup. If you're still experiencing hangs, check whether any rank is stuck on a non-blocking operation or a blocking collective. Adding `MPI.Barrier()` calls before `Finalize()` can help diagnose which rank is stuck.
✅ Expected Answer
Use `srun --mpi=pmix python myscript.py` (or `--mpi=pmi2` depending on the MPI build) inside an sbatch script that sets `--nodes`, `--ntasks-per-node`, and `--cpus-per-task` to match the layout your script expects. The hang is usually a collective (e.g., `MPI_Barrier`, `MPI_Bcast`) that an early-exiting rank skips — every rank must reach the same collective. Add `MPI.COMM_WORLD.Barrier()` before exit or wrap rank-specific work in conditionals that still participate in collectives, and call `MPI.Finalize()` cleanly (mpi4py usually handles this on interpreter shutdown).
