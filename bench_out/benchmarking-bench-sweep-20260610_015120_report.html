not deleted automatically - **Important**: Widespread computation against home directories causes poor performance for all users ## **Scratch Filesystems** There are actually **two types** of scratch storage: ### 1. **`/n/netscratch`** (Shared scratch) - **Purpose**: Temporary, high-performance space for I/O-intensive jobs and large data analysis - **Capacity**: 50 TB per lab (shared among lab members) - **Performance**: Excellent for HPC workloads (VAST parallel file system) - **Persistence**: **Volatile** - files older than 90 days are automatically purged; **not backed up** - **Best for**: Intermediate job output, large temporary files, data-intensive computation ### 2. **`/scratch`** (Node-local scratch) - **Purpose**: Directly connected temporary storage local to each compute node - **Performance**: Fastest option (directly attached to compute nodes) - **Persistence**: **Not shared across nodes** and **not persistent** - data is lost when job ends - **Best for**: Temporary files during job execution (like `/tmp`) ## **Recommendation for Intermediate Job Output** **Use `/n/netscratch`** for intermediate job output because: - It's designed for I/O-intensive workloads - It won't degrade performance for other users - It provides 90 days of retention for you to retrieve results - It's specifically intended for transient data that doesn't need permanent storage **Do NOT use home directories** for intermediate output from I/O-intensive jobs, as this will cause performance issues for all users. **Example workflow:** ```bash # Submit job writing intermediate output to netscratch #SBATCH --output=/n/netscratch/your-lab/your-project/job_%j.out # Or in your script: mkdir -p /n/netscratch/your-lab/your-project/intermediate # ... write intermediate files to /n/netscratch/your-lab/your-project/intermediate/ ``` **After job completion**, move any results you want to keep to permanent storage (home or lab directories). *Source: FASRC documentation on Cannon storage (docs.rc.fas.harvard.edu)*
✅ Expected Answer
Home directories are small (~100 GB), backed up, and intended for code, config, and important small files. `/n/holyscratch01/` is large, fast, and not backed up; it is purged on a published schedule and is the right place for intermediate job output and large working datasets. Move final results out of scratch before the purge window.

Based on the FASRC documentation, I can explain the issue and provide a solution. ## The Problem When using MPI with `mpi4py`, if one or more ranks finish their work and exit before all other ranks, the job will hang. This is because **MPI requires all ranks to synchronize before any rank can exit**. The MPI standard mandates that all processes in a communicator must reach a collective operation (like `MPI_Barrier` or `MPI_Finalize`) before the job can complete cleanly. ## The Solution You need to ensure **all ranks call `MPI.Barrier()` or `MPI.Finalize()`** before any rank exits. Here's the proper structure: ### Correct Python/mpi4py Pattern ```python from mpi4py import MPI import sys comm = MPI.COMM_WORLD rank = comm.Get_rank() size = comm.Get_size() # Your work here if rank == 0: # Rank 0 does some work pass else: # Other ranks do their work pass # CRITICAL: All ranks must synchronize before exiting comm.Barrier() # Optional: Finalize MPI cleanly comm.Finalize() ``` ### Slurm Submission Script ```bash #!/bin/bash #SBATCH -p batch #SBATCH -N 4 # Number of nodes #SBATCH -n 64 # Total number of MPI ranks #SBATCH -J mpi4py_job #SBATCH -o mpi4py.out #SBATCH -e mpi4py.err #SBATCH -t 01:00:00 module load python/3.8.5-fasrc01 source activate python3_env1 # Run with srun - Slurm handles the MPI initialization srun -n 64 python your_script.py ``` ### Key Points 1. **Use `srun` directly** - Slurm launches MPI tasks using PMI2/PMIx APIs when you use `srun -n <num_tasks> <command>` (as shown in the MPI Support documentation) 2. **All ranks must synchronize** - The Fortran example in the documentation shows `MPI_BARRIER` being called before `MPI_FINALIZE`, which is the same principle for Python/mpi4py 3. **Don't let any rank exit early** - Even if rank 0 finishes first, it must wait at `comm.Barrier()` for all other ranks 4. **Use `comm.Finalize()`** - This is the Python equivalent of `MPI_FINALIZE` in Fortran/C ## Why This Happens The documentation shows that MPI implementations require all tasks to participate in collective operations. When one rank exits without waiting for others, the remaining ranks hang waiting for a message that will never come. ## If You Still Have Issues If you're still experiencing hangs after implementing proper synchronization: 1. Check that all ranks are actually running (add `print(f"Rank {rank} starting")` at the beginning) 2. Verify your `srun` command has the correct number of tasks 3. Check for deadlocks in your collective operations (e.g., `comm.Allreduce`, `comm.Gather`) For further assistance, please attend FASRC office hours at https://www.rc.fas.harvard.edu/office-hours/ or email rchelp@rc.fas.harvard.edu.
