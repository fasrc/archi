## Context

The Slack bot (`src/interfaces/slack_bot.py`) is a thin client of `POST /v1/chat/completions` (design D1 of `openspec/changes/add-slack-service/design.md`). It acknowledges each Socket Mode request first, posts a placeholder, then replaces the placeholder with the answer text through `_deliver_answer()`. `build_messages()` drops the bot's own status lines (`_STATUS_TEXTS`) from the thread history that it sends as context.

The web chat stores ratings in table `feedback` (`src/cli/templates/init.sql`): `message_id` (FK to `conversations.message_id`), `feedback_ts`, `feedback` (`'like'`, `'dislike'`, `'comment'`), `feedback_msg`, `incorrect`, `unhelpful`, `inappropriate`; primary key `(message_id, feedback_ts)`. The insert SQL is `SQL_INSERT_FEEDBACK` (`src/utils/sql.py:16`). The Slack process already calls `PostgresServiceFactory.set_instance(...)` in `src/bin/service_slack.py`.

## Goals / Non-Goals

**Goals:** a Slack user rates an answer with one click (Helpful) or a short form (Not helpful); each rating becomes one `feedback` row that the Grafana panels already read.

**Non-Goals:** the streaming `/v1` path; a user column; emoji reactions; any change to `app.py`.

## Decisions

- **D1: buttons go in a second thread message, not in the answer.** Slack limits one `section` text to 3000 characters, and an answer can be up to `MAX_TEXT_CHARS` (39 000). A split into many sections can cut a mrkdwn link or code span in two. As a result, the answer delivery (`_deliver_answer()`) does not change. After a delivery that did not raise, when `archi_message_id` is a positive integer, the bot calls `chat_postMessage` in the same thread with `text=FEEDBACK_PROMPT_TEXT` (the notification fallback) and `blocks`: one `section` with the prompt, then one `actions` block with two buttons, `action_id` `archi_feedback_helpful` and `archi_feedback_not_helpful`, each `value=str(message_id)`. No prompt is posted after the error text, after a delivery that failed both attempts, or when the ID is `null`.
- **D2: the prompt is a status text.** Add `FEEDBACK_PROMPT_TEXT` to `_STATUS_TEXTS`, so `build_messages()` does not send the prompt as an assistant turn in later history.
- **D3: feedback failures are isolated.** A failure in the prompt post, in `views_open`, in `chat_postEphemeral`, or in the store logs an error and returns. It never changes or replaces the answer text and never raises out of `answer()` or `handle_request()`.
- **D4: one row for each rating, no delete.** Many Slack users can rate one answer. The web "delete then insert" toggle would erase other users' ratings, so the Slack path only inserts. `feedback_ts` is `datetime.now(timezone.utc)`; two clicks on one answer at different times give two rows.
- **D5: the message ID round-trips through Slack.** The button `value` and the form's `private_metadata` carry the ID, so the bot keeps no mapping table. `parse_message_id()` accepts only a string of ASCII digits that is a positive integer; anything else (empty, `"0"`, `"-1"`, `"1.5"`, non-string, `None`) gives `None`, a warning log, and no insert.
- **D6: click handling runs on the Socket Mode listener thread, not on the answer pool.** Slack expires a `trigger_id` after 3 seconds, so `views_open` runs at once in `handle_request()`. The answer pool can be busy for minutes. The `like` insert is one short statement and also runs inline.
- **D7: request routing.** In `handle_request()`, after the acknowledgement: `req.type == "events_api"` takes the existing path unchanged; `req.type == "interactive"` calls `self.handle_interactive(req.payload)`; other types return. `handle_interactive()`:
  - A retried envelope is handled once: before the insert, `interaction_key(payload)` keys a click by its user and `action_ts` and a form by its view ID, and the bot's `EventDeduper` drops a key it has seen. A payload with neither field is not deduplicated.
  - `payload["type"] == "block_actions"`: for each action whose `action_id` is one of the two IDs: helpful → insert `like` (all flags `NULL`, `feedback_msg` `NULL`), then `chat_postEphemeral(channel=<payload channel id>, user=<payload user id>, thread_ts=<container thread_ts if present>, text="Thanks for the feedback.")`; not helpful → `views_open(trigger_id=payload["trigger_id"], view=build_feedback_modal(message_id))`.
  - `payload["type"] == "view_submission"` with `view["callback_id"] == "archi_feedback_form"`: read `private_metadata` and the state values, then insert `dislike` with `incorrect`, `unhelpful`, `inappropriate` as booleans (selected → `True`, not selected → `False`) and the comment (Slack sends an empty optional input as `"value": null`, so read it as `(value or "")`; stripped; empty → `NULL`; capped at `MAX_FEEDBACK_COMMENT_CHARS` = 2000). The plain acknowledgement already sent closes the modal.
  - Anything else is ignored.
- **D8: the store is injected.** `SlackFeedbackStore(pool)` in `slack_feedback.py` has `insert(record)` that runs `SQL_INSERT_FEEDBACK` through `pool.get_connection()` and commits (`ConnectionPool.get_connection()` never commits; it only rolls back on error). A pooled connection can be dead after a Postgres restart while `conn.closed` is still false, so `insert()` retries on `psycopg2.OperationalError` or `psycopg2.InterfaceError` with the next connection from the pool, up to `MAX_INSERT_ATTEMPTS` = 6 attempts: the pool keeps up to `min_conn` (5) idle connections that can all be dead, it drops each broken one when it gets it back, and the sixth checkout opens a fresh one. The last failure raises to the caller, which logs it (D3). `SlackBot.__init__` takes `feedback_store=None`; `from_config()` builds it from `PostgresServiceFactory.get_instance().connection_pool` when an instance exists, else `None`. With no store, the bot posts no prompt (an unstorable click is worse than no button). Unit tests inject a fake store.
- **D9: `/v1` field.** `_non_streaming_response()` keeps `event.get("message_id")` from the `final` event and returns it as top-level `archi_message_id` when it is an `int` and not a `bool`; else `null`. Standard OpenAI clients ignore unknown fields. **Deviation from the premise of issue AC1:** the issue says a call without `X-OpenWebUI-Chat-Id` returns `null`. On `dev` a headerless call still stores a conversation: `openai_compat.py:318-327` passes `conversation_id=None`, `app.py:1742-1743` then creates a conversation, and `app.py:1912` inserts the messages, so the `final` event has an integer `message_id`. This change returns that real ID; it does not hide it. `null` appears only when the `final` event has no integer `message_id` (for example, a failed insert). The unit test proves the `null` arm with a `final` event that has no `message_id`; the PR body states this deviation.
- **D10: `ask_archi()` returns `AskResult(text, message_id)`**, a small `NamedTuple`. A missing or non-integer `archi_message_id` in the body gives `message_id=None`, not an error.

## Risks / Trade-offs

- A deployment that does not turn on interactivity shows buttons that do nothing (Slack shows a warning icon). The docs and the manifest change cover this.
- The FK on `feedback.message_id` rejects an ID that is not in `conversations` (for example, a forged `value`). The insert fails, D3 logs it, and no row is stored.
- Two users who click in the same microsecond on one answer collide on the primary key; one insert fails and is logged. This is accepted.
