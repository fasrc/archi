Answering-model replacement: moving archi off Qwen3.6 (2026-10)

Status: draft for operator review, 2026-10-13. Nothing has run. The decision rule is set (§6); its usability-floor numbers are proposals until the operator confirms them. The whole rule — floor, pilot cut and ranking — is then frozen into a timestamped pre-registration before the first Phase 1.4 pilot, because the pilot already applies the floor and the cut, as the Qwen3.8 comparison did (/scratch/a2rchi/bench-runs/ragas-qwen38/PREREGISTRATION.md).

Feature under test: the answering model, services.chat_app.providers.*.default_model / services.benchmarking.model: palmfuture/Qwen3.6-35B-A3B-GPTQ-Int4 → the best allowed candidate (§3). Everything else — code, prompt, corpus, judge, sampling, context window — is held fixed.

1. The question, and how the winner is chosen

Policy (operator, 2026-10-13): archi must move off Qwen, and the replacement cannot be a Chinese-developed model. Qwen3.6 leaves whatever it scores, so the question is not "is a candidate as good as Qwen3.6" but:

Which allowed open-weights model is the best answering model archi can run on the V100 host? — the best of what is allowed, as long as it is good enough to ship.

That gives a two-part rule (§6):

  1. Usability floor. A candidate must be fast and reliable enough for chat — absolute numbers, not "within X of Qwen3.6", because the move is not optional.
  2. Ranking. Among candidates that clear the floor, the one with the best answers wins.

Qwen3.6 stays in the benchmark as a reference, not a gate. It is the only yardstick on the same document set and it detects drift between runs. Each candidate's score minus Qwen3.6's is reported as the cost of the policy: how much answer quality the move gives up, if any.

Precedent. The 2026-10-12 Qwen3.8 comparison supplies the method this plan reuses (same document set, two runs per model, a plan fixed before the first run). Qwen3.8 itself is out under the policy.

2. What the candidate descriptions get wrong on this host

Checked on archi.rc.fas.harvard.edu on 2026-10-13 against the Volta vLLM image that serves both models today (/scratch/a2rchi/sifs/vllm_volta.sif, vLLM fork 1.1.0, transformers 4.57.6). That image is a hand-built Volta port with no build recipe on disk (see #286), so "does the image support it" is a hard constraint, not a version bump.

Claim in the candidate list Finding Evidence
Gemma 4 31B "fits on one V100 … maximum generation speed" Cannot be served on this image. Two independent gaps. (1) No Gemma 4 model code: upstream support arrived in vLLM 0.19.1 with transformers ≥ 5.5, and the image has neither, so vLLM's generic transformers fallback is out too. Gemma 4 31B: faster than today Wrong comparison. Qwen3.6 is a mixture-of-experts model that reads ~3B parameters per generated token; dense Gemma 4 31B reads all 31B. Dropping tensor parallelism removes the PCIe sync cost but not the ~10× more weight traffic. Llama 3.3 70B 4-bit "~40 GB across two V100s … plenty of VRAM for RAG context" Fits, but context memory is tight compared with today. Llama 3.3 70B keeps 320 KiB of cache per token; Qwen3.6 keeps ~20 KiB (only 10 of its 40 layers use full attention). Two cards at the 0.88 memory cap leave roughly 50k tokens of cache after weights: under two full 32k-token conversations at once. Qwen3.6 config.json; Llama 3.3: 80 layers × 8 KV heads × 128 dim × 2 × 2 bytes
Command R+ 4-bit "~60 GB fits cleanly across two 32 GB GPUs" Does not fit on two. Two cards at the 0.88 cap give 56.3 GiB for weights and cache; the 4-bit checkpoints are 54.6–60.4 GiB (58.6–64.9 GB), leaving at most ~1.7 GiB for working memory and cache — one 32k-token request alone needs 8 GiB. It needs all four GPUs, which means taking production Qwen3.6 down for the trial. 2 × 32 768 MiB × 0.88; the 0.95 cap crashed production in June (#43)
Command R+ "purpose-built for … multi-step tool use" vLLM cannot parse its tool calls. No vLLM parser reads Command R+'s tool-call format (an Action: line followed by a JSON block); the image's cohere_command3/cohere_command4 parsers target the later Command A models, and they also need the cohere_melody package, which is not installed. archi's agent cannot search without one. vLLM tool-calling docs; import cohere_melody → ModuleNotFoundError in the image
Command R+ as a current model The newest version is 08-2024, superseded by Command A (03-2025, 111B, same license) and Command A+ (05-2026, Apache 2.0, but ~132 GB at 4-bit, more than all four cards). Its license is CC-BY-NC 4.0, a "research release": internal university use is plausibly non-commercial, but that needs a legal reading. Cohere model cards
"AWQ or GPTQ" Both run on V100 in this fork (GPTQ from compute capability 6.0; AWQ from 7.0 through a fork-specific kernel). Marlin kernels (7.5+) and MXFP4 (8.0+) do not. Repo names are unreliable: several "AWQ"/"GPTQ" repos are really compressed-tensors, so read quantization_config.quant_method in config.json before downloading. get_min_capability() in the image's quantization modules

Disk: the Qwen3.8 weights (20 GB) were deleted on 2026-10-13, leaving 54 GB free on /scratch — room for a 4-bit Llama 3.3 70B (~40 GB) but not a 4-bit Command R+ (~58 GB). The further candidates screened in §3 are 15–18 GB each.

Publisher scores are leads, not evidence: they set the testing order and nothing else. Only NVIDIA's Lightning table compares against Qwen3.6 directly, and it shows a real gap on long-document reasoning, the closest public proxy for this job — an early estimate of the cost of the policy.

Reserves (tested only if the candidates below fail): IBM Granite 4.0 H-Small (superseded by Granite 4.1 on tool calling; carries the Mamba and expert-layer risks with no GPTQ checkpoint) and AI2 OLMo 3.1 32B Instruct (weakest tool calling of the set; its sliding-window layers fall off the image's fast V100 attention path).

Order. Phase 0 is hours per model, so every candidate gets it, most promising and smallest first; the 30-question pilot (Phase 1.4) then picks two for Phase 2.

  1. Nemotron 3 Nano — Qwen3.6's speed class, production's own tool parser, a tiny context cache.
  2. Mistral Small 3.2 — the lowest kernel risk: real GPTQ, plain dense model.
  3. Granite 4.1 30B — the strongest published tool-calling score; dense, so slower.
  4. Nemotron 3.5 Lightning — after a loader patch; the newest, and per NVIDIA the closest to Qwen3.6.
  5. Llama 3.3 70B — last: its 40 GB of weights need the others' deleted first, and it is the most likely to miss the speed floor.

Two fit on disk at a time with Phase 0.1's 10 GB margin (Nemotron 3 Nano + Mistral Small 3.2 ≈ 33 GB of the 54 GB free; three would leave under 6 GB). Before each further download, delete the weights of a candidate whose Phase 0–1 results are recorded; a finalist is re-downloaded for Phase 2. Each is under 20 GB, small enough for one GPU, so during Phases 0–1 two can run side by side (one per GPU, ports 8002 and 8003); Phase 2 serves the finalists the way they would be deployed. Gemma 4 and Command R+ each need an operator decision before Phase 0 (§9).

Worth adding if Gemma 4 is ported: google/gemma-4-26B-A4B-it — Google, Apache 2.0, a mixture-of-experts model with 128 experts, 8 used per token (~4B parameters per token, like Qwen3.6 and the Nemotron models). It shares the 31B's attention layout (head size 512 included), so one port covers most of both; its mixture-of-experts layers are additional work.

5. Phases

A candidate moves to the next phase only when every check in the current one passes. Phases 0–1 are hours and about $10–15 of judge spend per candidate; Phase 2 costs ~5–9 h of GPU time and $56–94 of judge spend per candidate (§7), so only the two best candidates out of Phase 1 reach it.

Phase 2 — same-corpus golden-set A/B

Adapt the Qwen3.8 runner (/scratch/a2rchi/bench-runs/ragas-qwen38/driver.sh; its run order, stack path and arm YAML names are hard-coded): one benchmark stack whose data manager never restarts, the benchmark container recreated per run with docker compose … up --no-deps, so every run sees one corpus.

  • Corpus. Either restart the archi-ragas-retrieval-ab stack (containers removed 2026-10-12, volumes kept) with data_manager.reset_collection: false in a copy of its config, or pay one fresh ~83-minute ingest. Record the corpus fingerprint and chunk count before the first run and after the last; a mismatch voids the comparison.
  • Order: Qwen3.6, A, B, B, A, Qwen3.6 (A and B are the two candidates out of Phase 1; with one, Qwen3.6, A, A, Qwen3.6). The finalists are counterbalanced so that drift in the judge, live load or the host over the sequence falls on both equally instead of deciding between them. Each finalist is served the way it would be deployed. If Llama 3.3 (L) is a finalist, its 39.5 GB and the other finalist's (X) checkpoint do not fit together with Phase 0.1's 10 GB margin. The order is then Qwen3.6, X, L, L, X, Qwen3.6: delete X after its first run, download L, delete L after its second run, re-download X. That adds two downloads (time them from Phase 0's and add them to the schedule), unless at least 15 GB is freed elsewhere on /scratch first.
  • Cold start for every candidate run. Restart the candidate's server before each of its runs (a few minutes each), whatever the order. The launchers keep --enable-prefix-caching, so without a restart a second consecutive run could reuse the first run's cached prompts and look faster. Qwen3.6 is production and is not restarted; its two runs are many hours apart, but its cache state cannot be controlled — a known asymmetry that can only flatter Qwen3.6's speed, which is reported, not gated. Fresh Qwen3.6 runs at both ends show net drift as a gap between them instead of letting it hide in the comparison. (The Qwen3.8 runs reused Qwen3.6 runs from earlier that day and had to list that as a weakness.)
  • Load asymmetry. Qwen3.6 on :8001 also serves live chat; the candidates have no other traffic. Run overnight. Any question in a Qwen3.6 run that overlapped a live chat turn (the benchmark container's timestamped log against Postgres turn times) is dropped from the speed figures, on both sides of each Qwen3.6 comparison; the number dropped is reported. Answer-quality scores are kept. The candidates' ranking is unaffected: no finalist shares its server with live traffic.
  • Identifier probe. Replay the 2026-10-13 kempner_rtx prompt (/scratch/a2rchi/bench-runs/qwen36-name-slip/replay.py, pointed at :8002): 200 draws, 8 identical requests at once, temperature 0.3. Qwen3.6 gave 0 / 200 wrong.
  • Capacity probe. 8 bank questions sent at once, 5 rounds, on each server; record p90 time per question. Every one of the 40 requests must return a valid, non-empty answer: an error or timeout fails the floor row instead of counting as a fast response. Production sees several chats at once; a smaller cache pool (§2) shows up here, not in the one-at-a-time benchmark.
  • Pre-registration was frozen before the first pilot (Phase 1); Phase 2 runs under it unchanged.

6. Decision rule (frozen before the first pilot)

Scored on the 104 bank questions (anchors excluded, as in the Qwen3.8 comparison). Each question's score is the mean of that model's two runs; differences are paired by question over questions scored in every run being compared.

1. Usability floor — every candidate run must clear every row. Absolute numbers, because the move is mandatory: the question is "what is the slowest, least reliable chat we would ship?", not "how close to Qwen3.6". The proposals below are about the worst Qwen3.6 has done plus a margin; Qwen3.8's numbers are shown for scale. The speed rows count every question asked, anchors included (what compare_runs.py's timing block measures); the other rows count the 104 bank rows. 2. Ranking — among candidates that clear the floor. Primary: answer_correctness, candidate against candidate, computed as follows. compare_runs.py compares one run file against one baseline file and cannot average two runs per model, so the primary statistic comes from a small analysis script adapted from the Qwen3.8 comparison's model_subsets.py, frozen with the pre-registration (its file hash recorded there):

  • per question, each finalist's score is the mean of its two runs;
  • d = A − B per question, over the bank questions scored in all four finalist runs;
  • SE = standard deviation of d / √n; σ = the larger of the two finalists' run-to-run spread (the absolute difference between a model's two run means), as in the Qwen3.8 comparison;
  • a difference counts only if |mean d| exceeds both 2·SE and 2·σ, and the per-run pairs (A run 1 vs B run 1, A run 2 vs B run 2, from compare_runs.py) agree in sign.

compare_runs.py still runs on every per-run pair, for its validity gates (G3–G10) and the G8 report below. Inside that noise, the tie is broken in order by faithfulness, mean seconds per question, give-up answers, then the simpler operation (fewer GPUs, no image patches). With a single candidate in Phase 2, there is nothing to rank: it is adopted if it clears the floor.

compare_runs.py's G8 row (anchors, plus "no other metric regressed past one noise unit") is reported for the finalist pair, with the runner-up as baseline and --noise-runs set to the runner-up's two runs, so every metric has a noise floor; where a metric's two-run σ is 0, --noise-floor takes the larger of the two finalists' two-run spreads for it, recorded as a deviation (the Qwen3.8 comparison's procedure). Without a floor, G8 skips that metric and can read clean when it was never tested. If the correctness winner shows a G8 regression on another metric, the choice goes to the operator with both rows in front of them, recorded in the ledger — it is not automatic either way. G8 is not a hard gate here because on 2026-10-12 it raised an alarm on Qwen3.6 against its own second run (easy-anchor scores, and answer_correctness against a two-run noise estimate of 0.0025). Against Qwen3.6, G8 is reported as part of the cost of the policy.

3. Cost of the policy — reported, not gated. Each candidate minus Qwen3.6 on every RAGAS metric, source accuracy, speed and judge cost per run, so the operator can say what the move cost. context_precision and context_recall can move too: the model writes the search queries.

If no candidate clears the floor: the operator chooses between relaxing the floor; the Gemma 4 port (§9); and the Anthropic standby already configured in dev.yaml (default_provider: anthropic, US-developed) — which sends every question off the host and is billed per token, so it is a decision, not a default.

9. Decisions

Made (operator, 2026-10-13): - The move off Qwen is policy; candidates cannot be Chinese-developed. The winner is the best allowed model that clears the usability floor (§1, §6). - Qwen3.8 stopped and disabled; its weights deleted.

Open: 1. The usability floor in §6 — confirm or change the numbers before the first pilot, when the rule is frozen: what is the slowest, least reliable chat you would ship? 2. Gemma 4: fund a separate spike — port the Gemma 4 architecture into the Volta fork and (most likely) extend its attention kernel to head size 512, with its own estimate and the rebuild risk of #286 (the image has no build recipe) — covering both 31B and 26B-A4B; or drop Gemma 4. 3. Command R+: recommend dropping. Trialling it needs all of: a tool parser written for its output format, a trial window with production failed over to the Anthropic standby (it needs all four GPUs), deleting more of the model cache, and a legal reading of CC-BY-NC for institutional use — for a model two generations old. 4. Fallback if nothing clears the floor (§6): relax the floor, fund the Gemma 4 port, or accept the off-host Anthropic standby. 5. License sign-off for the winner. Apache 2.0, OpenMDW-1.1 and the Llama 3.3 Community License are routine; the NVIDIA Nemotron Open Model License (Nemotron 3 Nano) adds an attribution notice and terminates if the user brings an IP suit against NVIDIA. 6. Who made the 4-bit weights. The policy is about who made the model, and a 4-bit checkpoint is the developer's weights re-packaged by whoever quantized them. Every checkpoint in §3 except Google's and Red Hat's comes from an individual Hugging Face account. Production's Qwen3.6 file (palmfuture/…) is one too, so this is not a new exposure, but it should be a decision. Options per candidate: a vendor-published 4-bit where one exists (Red Hat's Llama 3.3); otherwise quantize in-house from the developer's official repo with llm-compressor or GPTQModel on GPUs 0–1 (estimate: hours for a 24–32B model, longer for 70B); or accept the community checkpoint.
