# vLLM failure modes: a troubleshooting field guide

This page collects every vLLM-related failure the FASRC archi deployment has hit,
what the symptom looked like from the outside, what actually caused it, and the
commit that fixed it. It exists because these bugs are **hard to attribute**: most
of them look like "archi is broken" or "the model is broken" when the real fault is
a server flag, a chat-template setting, or a context budget.

**Who this is for:** anyone running archi (or any OpenAI-compatible client) against
a self-hosted vLLM server, especially with a *reasoning* model such as Qwen 3.x.

!!! note "Reference deployment"
    The fixes below were found on `archi.rc.fas.harvard.edu` serving
    `palmfuture/Qwen3.6-35B-A3B-GPTQ-Int4` on 2× Tesla V100-32GB via vLLM v1
    (Singularity), `--max-model-len 32768`, `--tensor-parallel-size 2`,
    `--enable-auto-tool-choice --tool-call-parser qwen3_coder`. Full host and flag
    inventory: [FASRC archi ops](fasrc_archi.md).

---

## Start here: the 60-second split

The single most useful thing you can do is decide **which of two classes** you are
in, because they have completely different fixes and the symptoms get conflated
constantly.

Run one failing prompt twice, against two different endpoints on the same server:

```bash
# Same model, same prompt, two endpoints.
curl -s http://<vllm-host>:<port>/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"<served-model-id>","messages":[{"role":"user","content":"say hello"}]}' \
  | tee /tmp/chat.json | python -m json.tool

curl -s http://<vllm-host>:<port>/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"<served-model-id>","prompt":"say hello","max_tokens":64}' \
  | python -m json.tool
```

| What you see | Class | Go to |
|---|---|---|
| `/v1/completions` returns text, `/v1/chat/completions` returns `"content": ""` | **Reasoning channel** — the answer is being routed into a discarded field | [1. Reasoning parser eats the answer](#1-the-reasoning-parser-eats-the-answer-empty-content) |
| Answers arrive but contain the model's own narration, or a bare `</think>` | **Reasoning channel** | [2. Orphan `</think>`](#2-orphan-think-tags-leak-reasoning-into-answers) |
| HTTP 500, worse as the conversation or tool use grows | **Request too big / server dead** | [3. Context-length 400](#3-context-length-400-crashes-the-request) |
| HTTP 500 and the server process is *gone* (no listener on the port) | **Server dead** | [4. CUDA OOM kills EngineCore](#4-cuda-oom-kills-enginecore-and-the-whole-server-exits) |
| Malformed or partial `tool_calls` in the response body | **Tool-call parser** | [7. Malformed tool calls](#7-malformed-tool-calls-an-exposure-we-have-not-yet-hit) |

!!! warning "An empty answer is not a server error in archi"
    This distinction matters for triage. In archi, an empty `content` from the model
    does **not** raise — `_build_output_from_messages`
    (`src/archi/pipelines/agents/base_react.py:1683`) degrades it to the literal
    string `"No answer generated by the agent."` at `:1699` and `:1701`. Likewise, a
    list-shaped `content` does not raise: `_message_content` (`:1582`) flattens it.

    So if you are getting a genuine **HTTP 500 / "server error"** rather than that
    placeholder string, the misshapen part of the response is **upstream of answer
    extraction** — malformed `tool_calls`, or an HTTP-level error from vLLM itself —
    *not* a content-shape problem. Two different bugs, two different fixes.

## 1. The reasoning parser eats the answer (empty `content`)

**Severity:** total outage of chat, while the server looks perfectly healthy.

**Symptom.** Every `/v1/chat/completions` reply comes back with `content` as an empty
string. `/v1/models` is HTTP 200. GPU utilization is normal. Raw
`/v1/completions` returns the answer correctly. Nothing logs an error, because
nothing *is* an error — the response is well-formed JSON that happens to contain
no answer.

**Cause.** Passing `--reasoning-parser qwen3` to a vLLM image whose custom qwen3
parser pins `prompt_has_open_think=True` at startup. The parser then assumes every
response *began* inside a reasoning block. When a reply contains no `</think>` to
close it, the parser routes **the entire answer into the reasoning channel**, which
is discarded, leaving `content` empty.

**Why it looks stochastic.** Whether the model emits a `</think>` on any given turn
is sampling-dependent. With the parser loaded and thinking enabled, some turns land
in `content` and some vanish entirely — so the failure rate rises with the number of
questions asked, exactly as an intermittent bug would. It is not concurrency and it
is not load.

**Fix.** Do not pass `--reasoning-parser` at all. It only helps when thinking is
*on*; with thinking off it is pure harm.

```diff
- --reasoning-parser qwen3 \
```

`--tool-call-parser qwen3_coder` is **independent** and unaffected — leave it in
place.

To run the model with thinking off, set it in the archi provider config instead, and
let it ride to vLLM as `chat_template_kwargs`:

```yaml
services:
  chat_app:
    providers:
      openai:
        extra_kwargs:
          extra_body:
            chat_template_kwargs:
              enable_thinking: false
```

**Ordering gotcha.** Restart the **server first**, then reseed/redeploy the app. The
reverse order brings a fresh app up against the old vLLM and serves empty answers
for the whole window. Wait for `GET /v1/models` to return 200 before step 2.

**Our commits:**

| What | Commit |
|---|---|
| Provider `extra_kwargs` (and therefore `extra_body` / `chat_template_kwargs`) actually reach `ChatOpenAI` | [`30cad280`](https://github.com/fasrc/archi/commit/30cad280643fc9b407d81e780ba3495618547d7f) |
| Harden config propagation so a stale cached config can't silently re-enable thinking | [`a8d61bcb`](https://github.com/fasrc/archi/commit/a8d61bcb7b695e8d59fc54b095f1be31ceb5303c) (PR #85) |
| The ops write-up: 0.88 OOM cap, no reasoning-parser, systemd unit | [`70c20654`](https://github.com/fasrc/archi/commit/70c206547b9a290ee3b556617da46e44d14db95d) (PR #46) |

Full detail: [Disabling model thinking](fasrc_archi.md#disabling-model-thinking-enable_thinkingfalse).

## 2. Orphan `</think>` tags leak reasoning into answers

**Severity:** users see the model's private reasoning as if it were the answer.

**Symptom.** Answers contain first-person planning narration and one or more bare
`</think>` tags with no opening `<think>`. A real answer we shipped to a user:

```text
The search results show a "Cannon Quickstart Guide" but the content isn't fully
visible... I should fetch the full document...
</think>

The document provides a "Pre-requisite steps" section... Let me search for more
specific information...
</think>

I've exhausted the search budget. Let me rely on the information I already have...
```

**Cause — two layers.**

1. *The trigger:* Qwen3's chat template, with reasoning enabled, prefills the
   opening `<think>` token into the **prompt**. So the model's **output** contains
   only the **closing** `</think>`.
2. *The defect:* archi's stripper matched only a balanced pair. A regex of
   `<think>(.*?)</think>` never matches an orphan close tag, so everything before it
   survived into the visible answer.

Reproduce the defect with pure stdlib, no repo needed:

```python
import re
pat = re.compile(r"<think>(.*?)</think>", re.DOTALL)
orphan = "reasoning text here\n</think>\n\nActual answer."
print(repr(pat.sub("", orphan).strip()))
# -> 'reasoning text here\n</think>\n\nActual answer.'   BUG: nothing stripped
```

**Fix.** Treat everything up to and including the **last** remaining `</think>` as
reasoning, keep only what follows as visible content, and preserve the reasoning in
the thinking channel rather than discarding it. See `_parse_thinking_content` at
`src/archi/pipelines/agents/base_react.py:247`.

This is defense in depth. The immediate trigger in our incident was a stale config
(a long-running container had cached its config at boot, before `enable_thinking:
false` was added — a restart cleared the live symptom). The stripper fix means a
stray tag never reaches a user even if thinking is accidentally on: bad config, a
redeploy dropping the flag, or a template that emits stray tags.

**Our commits:**

| What | Commit |
|---|---|
| Strip orphan `</think>` from visible output, incl. the stored/final answer | [`928f8a30`](https://github.com/fasrc/archi/commit/928f8a30754e7a5dfea60e83cae4d2fd7f488f98) (PR #121, closes [#84](https://github.com/fasrc/archi/issues/84)) |
| Tolerant category extraction, so reasoning traces don't break label parsing in ingestion | [`764f6108`](https://github.com/fasrc/archi/commit/764f6108c338661f5850e450d212712d2cd44925) (PR [#44](https://github.com/fasrc/archi/pull/44)) |

!!! warning "Still open: the streaming half"
    [#122](https://github.com/fasrc/archi/issues/122) tracks the remaining
    **live-streaming display** leak. `stream()` (`base_react.py:422`) and `astream()`
    (`:747`) call the parser on each accumulated prefix. For the orphan case,
    reasoning chunks arrive *before* the closing tag, so the prefix has no tag to
    strip and the reasoning is yielded as visible text. When `</think>` finally
    arrives, later chunks are stripped — but what was already displayed is never
    retracted. If you stream, you still have this.

## 3. Context-length 400 crashes the request

**Severity:** HTTP 500 on a brand-new conversation; correlates with tool use.

**Symptom.** A request dies with a vLLM 400. The failure rate rises with
conversation length and with how much the agent retrieves, which reads as
"stochastic, worse the more questions you ask."

Real timeline from our chat container logs, for the single query
*"What does sbatch --requeue do?"* on a fresh conversation:

```text
21:18:55.081  Forced initial retrieval ran -> 3221 chars
21:18:55.144  LLM call #1 -> 200 OK                    (context ~2-3k tokens)
   ...one round of model-chosen tool calls (9s)...
21:19:04.064  LLM call #2 -> 400: input = 85,316 tokens  (> 32,768 limit)
```

**One tool round added ~83k tokens (~330 KB).**

**Cause: model-controllable, unclamped tool parameters.** The document-fetch tool
exposed `max_chars` to the model with no upper clamp, and the file-search tool
exposed `max_results_override`, `max_matches_per_file`, `before`, `after`. Ingested
single documents are large enough to overflow a 32k window alone — one
`slurm.conf.html` at 299,847 bytes is roughly 75k tokens. LangGraph executes
parallel tool calls from one assistant turn, so several land in a single round.

!!! warning "Prompt instructions are not an enforcement boundary"
    We tried prompt-level mitigation three times ("keep `max_chars` at default", "at
    most 3 more tool calls"). Under a strict-grounding prompt the model ignored all
    of them. Clamp the parameter in code.

**The detector gotcha that will bite you specifically.** Our context-overflow guard
originally recognized only OpenAI-hosted phrasing (`context_length_exceeded`,
"maximum context length"). vLLM phrases it differently:

```text
You passed <N> input tokens ... the model's context length is only <M>,
resulting in a maximum input length of <M>
```

Until we matched that string, **the guard was completely inert against the very
error that motivated it**. If you copied a context-overflow handler from an
OpenAI-first codebase, assume it does not fire on vLLM until you prove otherwise.
See `_is_context_overflow_error` at `base_react.py:1861`, with the vLLM clause at
`:1873`.

**Fix, in layers:**

1. **Detect** vLLM's phrasing (above).
2. **Degrade** rather than crash — return a marked, degraded output instead of
   propagating the provider error. `_handle_context_overflow` at `base_react.py:1877`.
   Mark the degraded result (e.g. `context_overflow_retry`) so downstream consumers
   and benchmarks don't score it as a clean success.
3. **Re-raise everything else.** Only genuine context-length overflows are
   degradable; another 400 (a malformed parameter, say) must surface unchanged or you
   will hide real defects.
4. **Clamp at the tool boundary**, and enforce a per-invoke output budget. The
   retriever tool already does this via an `enforce_budget` callback checked on every
   call (`src/archi/pipelines/agents/tools/retriever.py:76`, `:114`); the catalog
   tools did not.

**Our commits:**

| What | Commit |
|---|---|
| Degrade gracefully on context-window overflow in `invoke()` | [`1c763e8e`](https://github.com/fasrc/archi/commit/1c763e8e0147eadb67f775dccadd84a79fca8aa5) (PR #91) |
| Cap `search_vectorstore_hybrid` calls per turn | [`38a2c55b`](https://github.com/fasrc/archi/commit/38a2c55b317f7ce8e9d9ab2b545585a3be1e9107) |

**Two things we got wrong, so you don't repeat them:**

- *The retry re-explodes.* Retrying by re-invoking the full agent with only the last
  human message makes the model repeat the same explosive tool round. Observed: first
  attempt 85,316 tokens, "retry" 85,408. Retry with a trimmed **message list**, and
  note that for agents with forced initial retrieval the message list *ends* with a
  large tool message — the very payload that overflowed — so `messages[-1:]` resends
  it. Select the last *human* message specifically.
- *The user-facing message lied.* Ours said "the conversation history has grown too
  large — start a new conversation," on a conversation with one message. Starting a
  new conversation reproduced the failure exactly.

**Observability gap worth fixing before you debug this.** Our trace rows were
persisted only for runs that *completed*, so the failing conversation had zero
tool-call rows and no trace — the exploding call's arguments were unrecoverable and
diagnosis meant reconstructing from `httpx` log lines. Persist tool-call arguments on
the failure path.

Still open, with the full three-PR plan:
[#139](https://github.com/fasrc/archi/issues/139).

## 4. CUDA OOM kills EngineCore, and the whole server exits

**Severity:** full outage, no auto-recovery.

**Symptom.** `CUDA out of memory` → `EngineDeadError` → `Application shutdown
complete` → process exits. After exit all GPUs read 0 MiB used. In vLLM v1 a dead
EngineCore is **fatal**: the API server does not recover on its own.

```text
RuntimeError: Worker failed with error 'CUDA out of memory. Tried to allocate
42.00 MiB. GPU 0 has a total capacity of 31.73 GiB of which 20.25 MiB is free.
... this process has 31.71 GiB memory in use.'
```

**Cause.** `--gpu-memory-utilization 0.95` on a 31.73 GiB V100. vLLM pre-reserves
its KV-cache pool at startup, but ~2–2.7 GiB of non-torch memory (CUDA context,
NCCL, cuBLAS/MoE workspaces) lives **outside** that budget. Each worker idled at
~31.5 GiB — a few hundred MiB below the ceiling — so a single long-context prefill
tipped it over. Note it failed trying to allocate just **42 MiB**: it was running at
the ragged margin.

**It was not concurrency.** Our first root-cause was "sustained concurrent traffic,"
and that was **disproven**. The crash came after ~16 h of *idle*, on a single long
prefill against an over-reserved baseline. It looked random; it was really the first
request large enough to exceed thin headroom.

**Fix.** `--gpu-memory-utilization 0.88` — ~4.5 GiB headroom, idle ~28.2 GiB. The KV
pool is still ~15 GiB / ~400k tokens, far more than a chat workload uses. Add
`--enable-log-requests` so the next event records the triggering request's shape.
Supervise the process (systemd) so a fatal EngineCore restarts.

!!! warning "Do not use expandable_segments on a Volta image"
    `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` crashes CUDA-graph capture
    (`VllmWorker died in compile_or_warm_up_model`) and only ever reclaimed ~135 MiB
    of fragmentation. It is widely recommended by the OOM message itself. Ignore it here.

Detail: [GPU memory & the 0.88 utilization cap](fasrc_archi.md#gpu-memory-the-088-utilization-cap).
Investigation history: [#43](https://github.com/fasrc/archi/issues/43).

## 5. The server itself 500s (middleware, not your request)

A prometheus/fastapi version incompatibility inside the vLLM image made the server
return HTTP 500 from its own middleware, independent of request content. We patched
it with a `sitecustomize.py` shim injected into the container.

This is worth ruling out early precisely because it is indistinguishable from an
application bug at the HTTP layer: same status code, no useful body. If 500s appear
on *every* endpoint including trivial ones, suspect the server, not the payload.

## 6. Benchmarking breaks separately from chat

If chat works but your benchmark harness fails against the same endpoint, the harness
is probably not speaking the right dialect.

**Symptom.** HTTP 404 from the vLLM endpoint, only from the benchmark path.

**Cause.** A `provider: local` config built an **Ollama** client, whose URL shape does
not match an OpenAI-compatible `/v1` endpoint. Chat was already routing through
`ChatOpenAI` and worked fine, which is what makes this confusing: same config key,
two different clients.

**Fix.** Auto-detect the mode. In archi the switch is `local_mode` in the provider's
`extra_kwargs` (`src/archi/providers/local_provider.py:73`), dispatching to
`_get_openai_compat_model` at `:109` for `openai_compat`.

| What | Commit |
|---|---|
| Benchmark SUT builds an `openai_compat` client for `/v1` endpoints | [`936a52f8`](https://github.com/fasrc/archi/commit/936a52f8cd27d2349607fd9c5fef851550e6eec5) (PR #74, closes [#73](https://github.com/fasrc/archi/issues/73)) |

**Also check:** if your golden-set answers were captured *while* failure mode 1 or 2
was live, the recorded answers are contaminated — empty strings or reasoning
narration scored as ground truth. Re-capture rather than trusting a bank that spans
the fix.

## 7. Malformed tool calls: an exposure we have **not** yet hit

We are flagging this because it is the best structural match for "the model's return
is misshapen in a way that breaks the agent response," and because archi has **no
defense against it**.

Our server runs `--enable-auto-tool-choice --tool-call-parser qwen3_coder`. If that
parser intermittently emits partial or invalid JSON arguments, the resulting message
has broken `tool_calls`. archi reads `message.tool_calls` directly at
`base_react.py:479`, `:486`, `:804`, `:806`, and:

```console
$ grep -rn "invalid_tool_calls" src/
$   # no output — no handling anywhere
```

LangChain surfaces unparseable tool calls in a separate `invalid_tool_calls`
attribute rather than raising at parse time. Nothing in archi inspects it. A
malformed call would therefore fail somewhere downstream, and it would look exactly
like the reported symptom: sampling-dependent (so stochastic and load-correlated),
agent-breaking, surfacing as a server error, and breaking benchmarking too.

**To confirm or rule this out**, capture a raw failing response body and check
whether `tool_calls[].function.arguments` is valid JSON:

```bash
python - <<'PY'
import json, sys
resp = json.load(open("/tmp/chat.json"))
for choice in resp.get("choices", []):
    for tc in (choice.get("message") or {}).get("tool_calls") or []:
        args = tc["function"]["arguments"]
        try:
            json.loads(args)
            print("ok  ", tc["function"]["name"])
        except json.JSONDecodeError as e:
            print("BAD ", tc["function"]["name"], "->", e, "|", args[:200])
PY
```

If you see `BAD`, you have found it, and the fix is to inspect `invalid_tool_calls`
and feed the model a corrective tool message instead of letting the broken call
through.

## 8. Adjacent "misshapen return" bugs worth knowing

Same defect *class* — a response whose shape violates an assumption — different
sources. All three are fixed.

| Symptom | Cause | Commit |
|---|---|---|
| Chat answer renders as a Python dict, e.g. `{'text': ...}` | Anthropic returns content **blocks** (a list), not a `str`. The OpenAI/vLLM path returns a plain `str`, so code written against vLLM breaks on an Anthropic failover. | [`98869080`](https://github.com/fasrc/archi/commit/988690808e1492a27d20b36207f76e2dbe6ed568) (PR #66, closes [#41](https://github.com/fasrc/archi/issues/41)) |
| HTTP 200 with the **wrong content** — the model answers a single character | An unvalidated request payload. A flat `["AI", "hello"]` instead of the nested `[["AI", "hello"]]` unpacked as `sender="A"`, `content="I"`. A 2-char sender silently discards the user's message; a longer one 500s. | [`c06fc45c`](https://github.com/fasrc/archi/commit/c06fc45c8eecde4ff9278b03ef18b17e24240ae2) (PR #179, closes [#167](https://github.com/fasrc/archi/issues/167)) |
| Ingestion labels come back empty for a reasoning model | Category-token scanning didn't tolerate chain-of-thought preceding the label. | [`764f6108`](https://github.com/fasrc/archi/commit/764f6108c338661f5850e450d212712d2cd44925) (PR [#44](https://github.com/fasrc/archi/pull/44)) |

The flattening helper is worth copying if you support more than one provider:
`flatten_message_content` in `src/archi/pipelines/agents/message_content.py:21`,
mixed in at `:55`. It leaves the `str` path byte-for-byte unchanged, so adding it
cannot regress a vLLM-only deployment.

## Diagnostics to collect before asking for help

Whether you are debugging this yourself or sending it to us, these five artifacts
distinguish every failure mode above. Without them, the two big classes are
genuinely indistinguishable.

1. **The exact exception and traceback** from the chat container
   (`docker logs <chat-container>`), not the user-visible message. The user-visible
   message is frequently wrong — ours actively misdirected debugging for a week.
2. **One raw response body** from a failing turn — the full
   `/v1/chat/completions` JSON, so `content`, `reasoning_content`, `tool_calls`, and
   `finish_reason` can all be read directly.
3. **Your exact vLLM launch line**, complete. Specifically: does it include
   `--reasoning-parser`? What is `--gpu-memory-utilization`? What is
   `--max-model-len`?
4. **Whether the server process is still alive** after a failure
   (`curl -fsS http://<host>:<port>/v1/models`). Alive means a request-level bug;
   gone means [#4](#4-cuda-oom-kills-enginecore-and-the-whole-server-exits).
5. **The token count in the 400**, if there is one. Compare it to
   `--max-model-len`. If it exceeds it, you are in
   [#3](#3-context-length-400-crashes-the-request), and the interesting question is
   which tool produced the payload.

One habit that saved us the most time: **always probe the model server directly**
before touching application code. A direct `curl` that also fails proves the fault is
server-side; a direct `curl` that succeeds where the app fails localizes it to the
client. And confirm your VPN is up first, so you don't misdiagnose a dropped tunnel
as a crashed server.
